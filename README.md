# Документация разработчика: Система экстракции данных (FFPA)

Данный документ содержит описание архитектуры, структуры файлов и технических особенностей системы автоматизированной экстракции фрагментов данных на базе LangGraph.

## 1. Структура проекта

Проект организован по модульному принципу для обеспечения возможности автономного тестирования и легкого рефакторинга.

*   `config.py` — Централизованная конфигурация, реестр моделей и глобальные параметры.
*   `agent_state.py` — Определение структур данных (TypedDict) для управления состоянием графа.
*   `llm_provider.py` — Фабрика для инициализации объектов языковых моделей и управления HTTP-клиентами.
*   `utils.py` — Вспомогательные функции для обработки текста, парсинга JSON и математических расчетов.
*   `extraction_graph.py` — Описание узлов (nodes) и логики переходов в графе.
*   `test_agent.py` — Скрипт для запуска тестов и имитации работы мастер-агента.

## 2. Описание файлов

### config.py
Содержит класс `Config(BaseSettings)`. 
*   **MODELS_REGISTRY**: Словарь доступных моделей. 
*   **Параметры контекста**: 
    *   `CONTEXT_WINDOW`: Максимальный размер контекста модели (например, $$60000$$).
    *   `CHUNK_THRESHOLD`: Коэффициент (например, $$0.20$$), определяющий порог включения чанкинга ($$20\%$$ от окна).
    *   `CHUNK_SIZE`: Размер одного чанка как доля от окна (например, $$0.15$$ или $$15\%$$).

### agent_state.py
Определяет `ExtractionState`.
*   Поле `model`: Строковое название модели, которое передается динамически.
*   Поле `raw_results`: Список словарей, использующий `operator.add` для накопления данных из параллельных веток.

### llm_provider.py
Отвечает за создание экземпляров `ChatOpenAI`.
*   **Важно**: Используется общий асинхронный клиент `httpx.AsyncClient`. В новых версиях библиотеки параметр должен называться `proxy=None` (в единственном числе).
*   **Безопасность**: Функция `get_model_by_name` извлекает учетные данные из конфига на основе `state['model']`.

### utils.py
Набор инструментов для низкоуровневой обработки.
*   `count_tokens_est(text)`: Оценка количества токенов. Используется коэффициент $$1:3$$ (один токен примерно равен трём символам).
*   `get_text_chunks(...)`: Логика разбиения текста с учетом `overlap`.
*   `robust_json_parser(text)`: Извлечение JSON-структур из текстовых ответов LLM с использованием регулярных выражений.
*   `sequence_reduce(...)`: Алгоритм слияния дубликатов на основе первичных ключей.

### extraction_graph.py
Основная логика LangGraph. Определяет три ключевых узла:
1.  `schema_node`: Анализирует начало документа и формирует JSON-схему.
2.  `map_extraction_node`: Выполняет экстракцию. Если объем данных превышает лимит, запускает цикл по чанкам через `asyncio.gather`.
3.  `reduce_node`: Финализирует данные, убирая избыточность.

## 3. Критические технические требования

### Авторизация и URL
При рефакторинге конфигурации моделей необходимо строго соблюдать следующие правила:
1.  **API Key**: Передается в чистом виде (например, `"sk-my-key-123"`). **Запрещено** добавлять префикс `Bearer`, так как библиотека LangChain/OpenAI добавляет его автоматически. Двойной префикс приведет к ошибке 401.
2.  **Base URL**: Должен указывать на корень API версии 1 (например, `http://10.0.x.x:8000/v1`). Не следует добавлять `/chat/completions` в конец строки.   

### Динамический чанкинг
Система автоматически адаптируется под размер контекстного окна выбранной модели:
*   Если количество символов в файле $$L > (CONTEXT\_WINDOW \times CHUNK\_THRESHOLD) \times 3$$, активируется разбиение на части.
*   Размер каждой части в токенах равен $$CONTEXT\_WINDOW \times CHUNK\_SIZE$$.
*   `CHUNK_OVERLAP` задается в символах для сохранения связности между кусками.

## 4. Этапы обработки данных

1.  **Инициализация**: В `test_agent.py` через `inputs` передается название модели из реестра.
2.  **Анализ схемы**: Узел `schema_gen` берет первые $$5000$$ символов файла для понимания структуры.
3.  **Экстракция (Map)**:
    *   Модель вызывается асинхронно.
    *   Если файл большой, он делится на $$N$$ частей.
    *   Для каждого чанка формируется отдельный запрос к LLM.
    *   Результаты собираются в единый список `raw_results`.
4.  **Слияние (Reduce)**:
    *   Функция `sequence_reduce` проходит по всем объектам.
    *   Объекты с одинаковым `primary_key` объединяются.
    *   Если в одном объекте поле пустое, а в другом заполнено — данные дополняются.

## 5. Рекомендации по отладке

*   Уровень логирования задается через `cfg.LOG_LEVEL`.
*   При возникновении `KeyError: 'model'`, проверьте, передается ли ключ `model` в начальный словарь `inputs` при вызове `app.ainvoke`.
*   Для ограничения нагрузки на локальные LLM (например, Ollama), используйте параметр `MAX_CONCURRENT_REQUESTS` в конфиге.
